# TPC-H engine comparison: InnoDB vs MySQL+DuckDB vs MariaDB+DuckDB vs native DuckDB

This document compares analytical query performance of four storage/execution
engines on the standard 22 TPC-H queries, on the **same host and the same data**:

| Engine | What it is |
|---|---|
| **InnoDB** | Vanilla MySQL 9.7 row store — no analytical pushdown (the baseline). |
| **MySQL+DuckDB (this project)** | The in-tree `ENGINE=DuckDB` engine: analytical queries auto-offload to DuckDB. |
| **MariaDB+DuckDB** | MariaDB's own `ENGINE=DuckDB` storage engine (`ha_duckdb.so`). |
| **native DuckDB** | The standalone DuckDB CLI on the same data — the analytical "ceiling". |

## Methodology

- **Host:** i7-13700H-class laptop, 20 logical CPUs, 62 GiB RAM, single NVMe.
- **Data:** TPC-H generated by DuckDB's `dbgen`, exported to per-table CSVs, loaded
  identically into every engine (quote-stripped so all engines store identical
  values). Two scale factors: **SF10** (≈60M lineitem rows) and **SF100** (≈600M).
- **Timing:** warm wall-clock, **min over iterations** (1 warm-up excluded). Each
  query runs through the engine's normal client (`mysql` / `mariadb` / `duckdb`).
- **Correctness:** every DuckDB-engine result set is compared (order-independent,
  numbers normalised to 4 decimals) against the oracle — InnoDB at SF1/SF10, and
  native DuckDB at SF100 (InnoDB is infeasible at 600M). All match unless noted.
- **Isolation:** at SF100 the engines are run **one at a time** (sequentially);
  two DuckDB instances cannot co-reside on a 62 GiB box without OOM.
- **Caveat:** measurement paths differ slightly (MySQL/InnoDB/native via
  `docker exec`; MariaDB via in-container client). Immaterial at these magnitudes.

All times in **seconds**. `ERR` = the engine could not run the query;
`>180 ⏱` = exceeded the 180 s cap (treated as a timeout).

**SF10 takeaways**
- **InnoDB is 100–340× slower** per query and **cannot finish 6 of 22** within
  180 s (the correlated-subquery + heaviest-scan queries). It needed **1317 s for
  just the 16 it completed**; the DuckDB engines do all 22 in ~15 s.
- The three DuckDB-based engines are **on par** (≈13–16 s total). This project's
  engine matches native DuckDB and MariaDB across the board; it wins notably on
  Q17 (0.12 vs MariaDB 0.42) and Q19 (0.15 vs 0.67).

**SF100 takeaways**
- **This project's engine is 22/22 correct** and tracks native DuckDB closely on
  21 of 22 queries.
- **MariaDB fails 2 queries (Q10, Q13)** and is markedly slower on the big joins —
  **Q9 115 s** (vs 21 s here / 20 s native), Q18 30 s, Q21 21 s.
- **Ingest:** loading 600M rows took **~20 min for this engine** (DuckDB `COPY`
  fast-path) vs **~80 min for MariaDB** (row-by-row, single-threaded — MariaDB's
  engine has no bulk-load fast-path). ≈4× faster ingest here.

### ⚠️ Caveat on Q15 (CTE) at SF100
The `1308.99 s` for this engine is a **memory-cap artifact, not a real result.**
This engine ran with `DUCKSDB_MEMORY_LIMIT=28GB` (deliberately capped below the
container's 44 GB cgroup so DuckDB spills to disk instead of the kernel OOM-killing
`mysqld` — the embedded engine carries mysqld + result-staging overhead on top of
DuckDB's working set). Under that cap, Q15's twice-referenced CTE spills heavily.
MariaDB ran at 48 GB with no such cap, so Q15 stayed in memory (2.45 s). **With
matched memory this engine runs Q15 in ~4 s, like native DuckDB.** Q15 is correct
in every configuration; only its time reflects the cap.

## Reproducing

- SF10 (InnoDB + this engine + native), one server:
  `IMAGE=ducksdb/mysql:9.7-duckdb-v0.2.0 SF=10 QTIMEOUT=180 bench/run-tpch22.sh`
- SF100 (this engine vs native, sequential phases, correctness + timings):
  `IMAGE=ducksdb/mysql:9.7-duckdb-v0.2.0 SF=100 MEM=44g DUCK_MEM=28GB bench/sf100-correctness.sh`
- MariaDB leg: `mariadb-bench/run-mariadb-tpch22.sh` (`NO_CLEAN=1 SF=100` for SF100).

CSVs are quote-stripped once so all engines load identical data; at SF100 the
engines are run one at a time to avoid co-resident OOM.
