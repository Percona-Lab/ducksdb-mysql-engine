# TPC-H Final 9 Constructs (13/22 → 22/22) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax. Phases are SEQUENTIAL (they share `engine/duckdb_pushdown.cc` + need a server build + correctness gate between each). Within a phase, validation of independent queries can fan out to parallel subagents. **Every subagent that runs a query against the engine MUST wrap it in `timeout` — a declined query falls back to a catastrophic row-by-row path (a prior workflow stalled 29 min on an un-timed-out Q11).**

**Goal:** Push the remaining 9 TPC-H queries (Q4, Q8, Q13, Q15, Q16, Q18, Q20, Q21, Q22) down to DuckDB with results byte-identical to InnoDB — or, where not provably equivalent, decline deterministically (correctness is the hard constraint; a faster wrong answer is a regression).

**Architecture:** Extend the existing recursive structured builder (`engine/duckdb_pushdown.cc`: `RenderQueryBlock` → `RenderFrom`/`RenderSelectItem`/`RenderExpr`/`RenderPredicate`, with `ExecutePushdown` staging the result). Four new capabilities, in dependency order: (1) make the pushdown hook FIRE for top-level queries whose FROM is a materialized derived table (a blocker found during Q13); (2) outer-join FROM-tree rendering; (3) semijoin/antijoin nest rendering (`SEMI`/`ANTI JOIN`); (4) CTE rendering. Plus a correctness gate on decimal division (Q8). The decline contract is the safety net throughout.

**Tech Stack:** C++17, DuckDB 1.5.3 (supports derived tables, scalar/correlated subqueries, `SEMI`/`ANTI JOIN`, `LEFT JOIN`, `WITH`), MySQL 9.7 (post-`JOIN::optimize` `Query_block`/`Query_expression`/`Table_ref`/`NESTED_JOIN`/`Item_subselect`; semijoin nests via `is_sj_nest()`/`is_aj_nest()`; join tree via `m_table_nest`/`nested_join`/`join_cond_optim()`), server patch `server-patches/0001-engine-query-pushdown.patch` (the `pushdown_select` hook), the TPC-H harness `bench/run-tpch22.sh`, MTR suite `duckdb`.

  - **MANDATORY:** adversarial verification (skeptic subagents + NULL-bearing micro-datasets) — silent wrong rows is the top hazard. md5-vs-InnoDB on SF1 is necessary but not sufficient.

## How to test (the gate for every phase)

Two checks per query: it **pushes** (`Ducksdb_pushdown_count` rises) and is **md5-identical to InnoDB**. Build + image, then load each query's tables into BOTH an `ENGINE=DuckDB` and an InnoDB database, run on each, compare sorted md5.

```sh
cd /home/corvin/AI_WORK/DUCKS/ducksdb-mysql-engine
docker run --rm -v "$PWD":/work -e REPO=/work -w /work ducksdb-builder:latest \
  bash -lc 'cmake --build vendor/mysql-server/build --target mysqld -j"$(nproc)"'   # source-only ⇒ no reconfigure
BUILD_TYPE=RelWithDebInfo scripts/release-image.sh ducksdb/mysql:9.7-duckdb-pN
# regression (the existing pushers must stay green):
SF=1 ITERS=1 ONLY="1 3 5 6 10 12 14 19" CPUS=10 MEM=8g QTIMEOUT=90 \
  IMAGE=ducksdb/mysql:9.7-duckdb-pN bash bench/run-tpch22.sh    # expect passed(match)=8 mismatch=0
docker volume prune -f   # the harness leaks anonymous datadir volumes — reclaim every run
```

Per-query correctness uses the direct load-both-engines + md5 pattern (the subquery queries have no `qNN.mysql.sql`, so the harness can't gate them — run them directly). The reusable validation harness from this session: load tables via `LOAD DATA LOCAL INFILE … FIELDS TERMINATED BY '|'`, DDL from `bench/run-tpch22.sh` `ddl_mysql()`, query SQL from `bench/data-sf1/queries/qNN.duckdb.sql`, call the `mysql` BINARY under `timeout`, compare `sort | md5sum`.

**Decline diagnostics:** boot mysqld with `DUCKSDB_PD_TIMING=1`; `[pd-decline-at] <section>` logs the specific decline (grep the line BEFORE the generic `query-block`); `[pd-gen]` logs the generated SQL; absence of any `[pd]` line means the hook never fired (Phase 1's signature). Merge-vs-materialize and semijoin flattening are **data-dependent** — always probe on loaded SF1 data, not empty tables.

## Phase 3 — Semijoins: IN / EXISTS (Q4, Q18, Q20, Q21-part)

After `JOIN::optimize`, `IN`/`EXISTS` predicates are flattened into **semijoin nests** (`Table_ref::is_sj_nest()`), not `Item_subselect`. Render the nest as a DuckDB `SEMI JOIN`.

- [ ] **Step 1:** Probe (loaded SF1, `DUCKSDB_PD_TIMING`) the post-optimize shape of Q4/Q18: confirm a `Table_ref` with `is_sj_nest()` appears in `m_table_nest`, and find its inner tables (`nested_join->m_tables` / `nested_join->sj_inner_tables`) and the semijoin condition (`sj_cond()` / the nest's `join_cond()`). Document the exact accessors.
- [ ] **Step 2:** In `RenderJoinList`, replace the `is_sj_nest()` decline with: `" SEMI JOIN " + "(" + RenderJoinList(nest inner tables) + ")" + " ON (" + RenderPredicate(sj condition) + ")"`. Decline if: the inner has a GROUP BY/HAVING that the nest form can't express inline (Q18's inner is `GROUP BY l_orderkey HAVING sum>…` — verify DuckDB SEMI JOIN against a grouped subquery works, else render the inner as a derived `(SELECT … GROUP BY … HAVING …)` and SEMI JOIN to it), or any sub-render declines.
